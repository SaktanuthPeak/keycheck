# บทที่ 5 สรุปผลและการประเมินวิธีการ

## 5.1 สรุปสิ่งที่พัฒนาและผลที่ได้เทียบกับวัตถุประสงค์

โครงงานนี้พัฒนา KeyCheck ระบบตรวจคีย์แคปผิดตำแหน่งจากภาพถ่ายคีย์บอร์ดหนึ่งภาพ โดยผู้ใช้แตะจุดอ้างอิง 4 จุด (ปุ่ม Q, P, M, Z) ระบบปรับภาพให้ตรงด้วย homography ตรวจจับกรอบคีย์แคป อ่านตัวอักษร จับคู่ปุ่มกับ 26 ช่องด้วยตำแหน่งโดยใช้ Hungarian algorithm และตัดสินแต่ละช่องเป็นถูก ผิด หรือไม่แน่ใจ พร้อมแนะนำการสลับ ส่วนประกอบของระบบ ได้แก่ แพ็กเกจ `ai/` ที่มี pipeline ทั้งหมด ตัวตรวจจับ YOLO11n และ Faster R-CNN ตัวจำแนก ResNet18 27 คลาส และ baseline ที่ไม่ใช้ detector พร้อม Backend FastAPI ที่มีคิวงานแบบ lease/heartbeat และเว็บ SvelteKit ที่มีตัวแตะจุดอ้างอิงและการแสดงผลซ้อนบนภาพ

เมื่อเทียบกับวัตถุประสงค์ในหัวข้อ 1.2 ได้ผลดังนี้

1. **ชุดข้อมูลและกระบวนการเตรียมข้อมูล (ข้อ 1) ทำได้บางส่วน** สร้างกระบวนการนำเข้า ตรวจสอบ แบ่งชุดแบบ leave-brand-out และสร้างชุดประเมินครบ แต่ใช้ข้อมูลตัวแทน QWERTZ 5,254 ภาพ ยังไม่ได้เก็บข้อมูล QWERTY ที่ถ่ายเอง
2. **ฝึกและเปรียบเทียบ detector อย่างน้อย 2 แบบ (ข้อ 2) สำเร็จ** YOLO11n ได้ mAP50-95 เท่ากับ 0.854 และ Faster R-CNN ได้ 0.815 บน Validation
3. **อ่านตัวอักษรและตรวจผิดตำแหน่ง (ข้อ 3) สำเร็จในระดับ pipeline** ตัวเลขรายตัวชี้วัดของระบบปลายทางยังต้องดึงจากรายงาน Q6
4. **แสดงสถานะ "ไม่แน่ใจ" แทนการเดา (ข้อ 4) สำเร็จ** มี `uncertain` รายช่อง และ `LAYOUT_MISMATCH` ทั้งภาพ
5. **เว็บแอปพลิเคชันต้นแบบ (ข้อ 5) สำเร็จ** flow ครบ มีชุดทดสอบ e2e แต่ยังไม่ได้รันชุดทดสอบ Frontend/Backend ในรอบทำรายงาน และยังไม่ได้ทดสอบกับผู้ใช้จริง
6. **ประเมินรายโมดูลและปลายทาง (ข้อ 6) ทำบางส่วน** รายโมดูลครบ (OCR, detector) ส่วนปลายทางมีค่า objective แต่ตารางรายสถานการณ์ละเอียดยังไม่อยู่ในรีโป และยังไม่ได้ประเมินบนคีย์บอร์ดที่ไม่เคยเห็นเป็นตัวเลข เพราะชุด Test ยังล็อกอยู่

### เกณฑ์ความสำเร็จและผลที่ได้

โครงงานไม่ได้กำหนดเป้าหมายความแม่นยำหรือเวลารอเป็นตัวเลขไว้ล่วงหน้า เพราะ Technical Specification ระบุให้ตกลงหลังทำ Pilot และ benchmark อุปกรณ์ เกณฑ์ที่มีอยู่จริงมาจากไฟล์ config ของการทดลองและข้อกำหนดเชิงฟังก์ชันใน Specification ตารางที่ 28 เทียบเกณฑ์เหล่านั้นกับผลที่ได้ โดยสถานะ "ผ่านตามการออกแบบ" หมายถึงบังคับด้วยโค้ดแต่รายงานนี้ยังไม่ได้รันชุดทดสอบยืนยัน

| # | เกณฑ์ | ที่มา | ผลที่ได้ | สถานะ |
| --- | --- | --- | --- | --- |
| 1 | OCR: reject rate ≤ 10% | config Q3 | ต่ำสุด 16.1% | **ไม่ผ่าน** จึงเปลี่ยนเป็นตัวจำแนก |
| 2 | false-alarm ของภาพที่ประกอบถูก (S1) ≤ 2% | config Q6 (บังคับด้วย penalty ตอนจูน) | `[รอตัวเลข]` | ยังยืนยันไม่ได้ |
| 3 | ภาพถูกที่ถูกปฏิเสธ ≤ 2% | config Q6 | `[รอตัวเลข]` | ยังยืนยันไม่ได้ |
| 4 | S4a (แตะเลื่อน) ถูกปฏิเสธด้วย `LAYOUT_MISMATCH` ≥ 80% | พื้นขั้นต่ำใน objective | 91% ตามคอมเมนต์ใน config (รอบจูนก่อนหน้า); ชุดที่ commit `[รอตัวเลข]` | ผ่านในรอบก่อน ต้องยืนยันซ้ำ |
| 5 | เปรียบเทียบอย่างน้อย 2 detector และ 1 baseline บน Test เดียวกัน | Spec §9.3 | ทำบน Validation เท่านั้น ไม่ได้รัน Test | ทำบางส่วน |
| 6 | ผลตรวจบันทึกเวอร์ชันโมเดลและ layout | Spec §9.3 | ผลมี `model_bundle_id`, `layout_id`, `layout_version` | ผ่านตามการออกแบบ |
| 7 | ภาพผิดชนิดหรือไม่ครบได้ข้อความแก้ไข ไม่เกิด server crash | Spec §9.3 | มีรหัสข้อผิดพลาดและข้อความภาษาไทย; ชุด e2e ยังไม่ได้รัน | ยังยืนยันไม่ได้ |
| 8 | ไม่ประกาศว่าถูกทั้งหมดถ้ายังมี `uncertain` และไม่เสนอสลับถ้าหลักฐานไม่พอ | Spec §9.3 | บังคับใน `suggest()` และ UI | ผ่านตามการออกแบบ |
| 9 | ไม่เข้าถึงภาพหรือผลของ session อื่น | Spec §9.3 | ตรวจเจ้าของทุก endpoint ตอบ 404 | ผ่านตามการออกแบบ (test Backend ยังไม่ได้รัน) |
| 10 | เป้าหมายความแม่นยำและเวลารอเป็นตัวเลข | Spec: ตกลงหลัง Pilot | ไม่ได้กำหนด | ไม่ตัดสินผ่านหรือไม่ผ่าน |

ตารางที่ 28 แสดง เกณฑ์ความสำเร็จเทียบกับผลที่ได้

สรุปการวิเคราะห์ว่าผลเป็นไปตามเป้าหมายหรือไม่: เป้าหมายเชิงสถาปัตยกรรมและฟังก์ชันสำเร็จตามที่ออกแบบ (วัตถุประสงค์ข้อ 2, 4 และ 5) ส่วนเป้าหมายเชิงความแม่นยำของระบบปลายทาง **ยังตัดสินไม่ได้** เพราะตัวเลขที่เป็นหลักฐานหลักยังไม่อยู่ในรีโป และชุด Test ซึ่งเป็นหลักฐานที่เชื่อถือได้ที่สุดยังไม่ได้รัน

ข้อค้นพบสำคัญ คือ (1) OCR สำเร็จรูปไม่เหมาะกับตัวอักษรเดี่ยวบนปุ่ม แม้ปรับครอปและความละเอียดดีที่สุดยังปฏิเสธไม่อ่านอย่างน้อย 16% (accuracy สูงสุด 0.82) การเปลี่ยนเป็นตัวจำแนกแบบ closed-set จึงเป็นการเปลี่ยนที่สำคัญที่สุดของโครงงาน (2) ตรวจจับตำแหน่งปุ่มบนภาพที่ปรับให้ตรงแล้วเป็นปัญหาที่ง่าย (mAP50 > 0.97 ทั้งสองโมเดล) ความยากอยู่ที่การอ่านและการตัดสินใจ (3) ประโยชน์ของ detector เหนือ baseline มีจำกัดบนข้อมูลตัวแทน เฉพาะ YOLO11n ที่นำเล็กน้อย และ (4) การออกแบบที่ปฏิเสธและงดตอบหลายชั้นทำให้ threshold ที่เลือกเข้มงวด (`ocr_score_min` 0.98–0.99) ระบบจึงยอมลดจำนวนช่องที่ตอบเพื่อไม่ตอบผิด

## 5.2 การประเมินวิธีการที่ใช้และสถาปัตยกรรมระบบ

**การแยกเป็น `ai/` Backend และ Frontend** ทำให้ logic ของ pipeline อยู่ที่เดียวและใช้โค้ดชุดเดียวกันทั้งตอนประเมินและตอนให้บริการ ผลที่วัดจึงสะท้อนระบบจริง Backend ไม่ต้องรู้เรื่อง machine learning และ Frontend รู้เพียง API ที่สร้าง type จาก OpenAPI ทำให้ตรวจความสอดคล้องได้ตอน compile แลกกับการต้องดูแลสัญญา (contract) ระหว่างสามส่วนให้ตรงกัน ซึ่งแก้ได้ด้วยเอกสาร `api-contract.md` ที่ล็อกไว้และ test ที่ตรวจ contract ทั้งสองฝั่ง

**การแยก "หลักฐาน" ออกจาก "การตัดสิน"** ทำให้จูน threshold หลายร้อยชุดได้โดยไม่รันโมเดลซ้ำ ซึ่งสำคัญเมื่อการรันโมเดลใช้เวลาเป็นชั่วโมง ข้อแลกเปลี่ยนคือต้องดูแล cache ให้ตรงกับเวอร์ชันของโมเดลและโค้ด ซึ่งแก้ด้วย fingerprint ของน้ำหนัก config และซอร์ส

**การจับคู่ด้วยตำแหน่งอย่างเดียว** ด้วย Hungarian algorithm เป็นหัวใจที่ทำให้มองเห็นปุ่มที่ถูกสลับ และ dummy ทำให้ช่องว่างและกรอบเกินไม่ทำให้ผลเพี้ยน

**กลไกงดตอบและปฏิเสธหลายชั้น** (ช่อง `uncertain`, layout-fit, `ref_invalid`, `mismatch_min_wrong`) ลด false-alarm ได้ตามเจตนา ดังเห็นจากภาพ corsair14 ที่ `uncertain` 12 ช่องแต่ `incorrect` เป็นศูนย์ ข้อแลกเปลี่ยนคือ coverage ต่ำลงกับคีย์บอร์ดที่อ่านยาก

**การใช้ Notebook เดียวแบบ stage cache และการล็อกชุด Test** ทำให้การทดลองทำซ้ำได้ ข้ามขั้นที่ไม่เปลี่ยนได้ และป้องกันการจูนตามผล Test โดยไม่รู้ตัว อย่างไรก็ตามผลการทดลองที่เก็บไว้เฉพาะใน output ของ Notebook ทำให้อ้างอิงและตรวจสอบย้อนหลังไม่ได้ (ดู 5.3 ข้อ 6)

**ระบบเว็บ** แยกงานประมวลผลออกเป็น worker พร้อม lease ทำให้ทนต่อการล้มของ worker และการตรวจไฟล์ก่อนถึงโมเดลหลายชั้นลดความเสี่ยงด้านความปลอดภัย แต่ยังไม่ได้ทำ load test และยังไม่ได้ทดสอบกับผู้ใช้จริง

## 5.3 ปัญหาที่พบ

1. **ปัญหา OCR สำเร็จรูปอ่านตัวอักษรเดี่ยวบนปุ่มไม่ได้ตามเกณฑ์** ไม่มีแถวใดของการทดลอง Q3 ผ่านเกณฑ์ reject ≤ 10% และตัวอักษร I, O แทบอ่านไม่ได้ เกิดจากโมเดลออกแบบมาสำหรับข้อความหลายตัวอักษร และตัวอักษรบนปุ่มมีฟอนต์หลากหลาย แก้โดยฝึกตัวจำแนก ResNet18 27 คลาส (A–Z + OTHER) ด้วย transfer learning
2. **ปัญหาโค้ดเลือกค่าไม่ตรงกับตารางผลทดลอง** เมื่อไม่มีแถวผ่านเกณฑ์ ฟังก์ชัน `run_q3` คงแถวแรกไว้ (ppu 64 / `key_full`) ทั้งที่ `key_center_0.7` ดีกว่ามาก เกิดจากการเขียนเงื่อนไข fallback ไม่ครอบคลุมกรณีที่ไม่มีแถวผ่าน แก้เบื้องต้นโดยบันทึกในเอกสาร bundle และตั้งค่า baseline เป็น `key_center_0.7` ด้วยมือ ควรแก้ที่โค้ดให้เลือกแถวที่ดีที่สุดเมื่อไม่มีแถวผ่าน
3. **ปัญหาจุดอ้างอิงเลื่อนหนึ่งช่องไม่ถูกปฏิเสธ** รอบ smoke ได้ผล 0/13/13 แทน `LAYOUT_MISMATCH` เพราะ detector เห็นปุ่มข้างเคียงครบ layout-fit จึงผ่าน และ `ref_invalid_max` เป็น `null` แก้โดยเพิ่มเงื่อนไข `mismatch_min_wrong` และกำหนดพื้นขั้นต่ำ 80% ของ S4a ใน objective เพื่อไม่ให้การจูนปิดการตรวจ layout
4. **ปัญหาคีย์บอร์ด Ortholinear ที่ผู้ใช้แตะจุดถูกต้องไม่ถูกปฏิเสธ** (test แบบ xfail) เพราะ homography 4 จุดดูดซับกริดเรียงตรงไว้ มีเพียงแถว A ที่คลาด 0.125u การเพิ่มเกณฑ์การเยื้องรายแถวจะปฏิเสธคีย์บอร์ดปกติบางรุ่นด้วย (ในชุด Kaggle ที่ถูกต้องคลาดถึง 0.12u) จึงยังไม่แก้ และถือเป็นช่องว่างของวัตถุประสงค์ข้อการปฏิเสธรุ่นที่ไม่รองรับ แนวทางแก้ที่เป็นไปได้คือเก็บข้อมูลคีย์บอร์ดแบบ Ortholinear มาตรวจ หรือเพิ่มการตรวจด้วยข้อมูลเชิงภาพ
5. **ปัญหา detector ที่ยังไม่ฝึกให้กรอบจำนวนมาก ทำให้อ่านตัวอักษรช้า** ราว 300 กรอบ ≈ 15 วินาทีบน CPU เกิดจากการอ่านทุกกรอบใกล้บล็อก แก้โดยให้ Inspector จับคู่ก่อนแล้วอ่านเฉพาะกรอบที่ถูกจับคู่ (≤ 26 ครอป) และมี test พิสูจน์ว่าผลเท่ากับเส้นทางประเมิน
6. **ปัญหาผลการทดลองบางส่วนไม่อยู่ในรีโปและผล Q6 สองชุดไม่สอดคล้องกัน** Notebook เก็บ output เฉพาะรอบที่ใช้ PP-OCR ขณะที่ `thresholds.yaml` มาจากรอบที่ใช้ตัวจำแนก และไม่มีผล Q3b และตาราง S1–S4 ในรีโป ทำให้รายงานต้องทำเครื่องหมาย `[รอตัวเลข]` แก้โดยต้องรัน Q6 ซ้ำและบันทึก `val_report.md` เข้ารีโปเป็นนโยบายถาวร
7. **ปัญหาข้อมูลตัวแทนไม่มีปุ่มอักษรไทยและไม่มีตัวอย่างปุ่มหายบางส่วนเพียงพอ** S4b ใน Validation มี 0 รายการ แก้บางส่วนโดยสังเคราะห์อักษรไทยลงบนครอปตอนฝึก แต่ยังพิสูจน์บนปุ่มไทยจริงไม่ได้

## 5.4 ข้อจำกัดของโครงงาน

1. **ข้อมูลเป็นข้อมูลตัวแทน** ภาพคีย์บอร์ด QWERTZ จากสินค้าหรือเว็บ ไม่ใช่ภาพถ่ายมือถือของคีย์บอร์ด QWERTY จึงอ้างความแม่นยำของระบบกับการใช้งานจริงไม่ได้
2. **ยังไม่ได้รันชุด Test (Q7)** ตัวเลขทั้งหมดเป็นผลบน Validation ที่ใช้จูน threshold ด้วย จึงมี optimism bias
3. **อักษรไทยเป็นแบบสังเคราะห์** พิสูจน์ได้เพียงว่าโมเดลไม่พังเมื่อมีอักษรไทยเพิ่ม ไม่ใช่ว่าใช้ได้กับปุ่มไทยจริง
4. **ชุดประเมินบางชุดเล็กเกินไป** S4b ใน Validation มี 0 รายการ S4c มี 11 รายการ และ Validation มี 215 ภาพจาก held-out 2 ยี่ห้อ
5. **ผล Q6 ที่บันทึกไว้สองชุดไม่สอดคล้องกัน** ลำดับ YOLO11n กับ Faster R-CNN ขึ้นกับตัวอ่านที่ใช้ และตัวเลขบางส่วนไม่อยู่ในรีโป
6. **ผู้ใช้ต้องแตะจุดอ้างอิง 4 จุดเอง** ความผิดพลาดของการแตะเป็นแหล่ง error ที่ระบบลดผลได้แต่ไม่หมด
7. **ขอบเขต layout จำกัด** ใช้ได้กับ QWERTY แถวเยื้อง ตัวอักษร A–Z เท่านั้น และคีย์บอร์ด Ortholinear ที่ผู้ใช้แตะจุดถูกต้องยังไม่ถูกปฏิเสธ (หัวข้อ 5.3 ข้อ 4)
8. **ความปลอดภัยของน้ำหนักโมเดล** Faster R-CNN โหลดด้วย `torch.load(weights_only=False)` ใช้ได้เฉพาะ bundle ที่สร้างเอง ห้ามรับน้ำหนักจากผู้ใช้
9. **ยังไม่ได้ทดสอบกับผู้ใช้จริงและยังไม่ได้ทำ load test** รวมถึงยังไม่ได้รันชุดทดสอบ Backend และ Frontend ในรอบทำรายงาน

## 5.5 แนวทางพัฒนาต่อ

1. **รัน Q6 ซ้ำให้ครบด้วยตัวอ่านที่ใช้จริง** แล้วเก็บ `val_report.md` และ `val_<detector>.json` เข้ารีโป เพื่อให้บทที่ 4 มีตาราง S1–S4 ครบและแก้ความไม่สอดคล้องของผลสองชุด พร้อมดึงผล Q3b (`metrics.json`)
2. **เก็บข้อมูลคีย์บอร์ด QWERTY จริงตามขอบเขต Tier 2** คีย์บอร์ด 8–12 รุ่น (รวมแบบไทย-อังกฤษ) ตามคู่มือถ่ายและ annotate ที่เตรียมไว้ โดยข้อมูลจากเว็บหรือสาธารณะใช้เฉพาะ Train ของ detector และทำ leave-keyboard-out ที่แท้จริง
3. **รัน Q7 ครั้งเดียว** หลัง commit ไฟล์ที่ freeze แล้ว และรายงานแยกยี่ห้อที่เคยเห็นและไม่เคยเห็น
4. **แก้ฟังก์ชัน `run_q3`** ให้เลือกแถวที่ดีที่สุดเมื่อไม่มีแถวผ่านเกณฑ์ และพิจารณาตรวจ Ortholinear ด้วยข้อมูลจริง
5. **วัดประสิทธิภาพให้ครบ** median และ P95 ต่อขั้นบน hardware สะอาด เวลาของตัวจำแนกเทียบ PP-OCR และหน่วยความจำ
6. **ตรวจหามุมอัตโนมัติ** เช่น ตรวจบล็อกตัวอักษรแล้วเสนอจุดตั้งต้นให้ผู้ใช้ปรับ เพื่อลดภาระการแตะ 4 จุด
7. **ทดสอบกับผู้ใช้จริงและ layout อื่น** (ISO ที่ปุ่มเยื้องต่างกัน, TKL/60%) พร้อมทำ load test
8. **ปรับปรุงตัวอ่าน** ทดสอบตัวจำแนกขนาดเล็กกว่า (เช่น MobileNetV3) เพื่อลดเวลา CPU และทำ calibration ของคะแนนความมั่นใจ (temperature scaling) เพื่อให้ `ocr_score_min` มีความหมายเชิงความน่าจะเป็น
9. **Active learning** นำภาพที่ระบบตอบ `uncertain` มาให้ annotate เพิ่มเพื่อเพิ่มข้อมูลที่ยากที่สุด
