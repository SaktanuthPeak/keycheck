# บทที่ 1 บทนำ

## 1.1 ที่มาและความสำคัญ

คีย์บอร์ดแบบกลไก (mechanical keyboard) เป็นอุปกรณ์ที่ออกแบบให้ถอดคีย์แคป (keycap) ออกจากสวิตช์ได้ ผู้ใช้จึงนิยมถอดเพื่อทำความสะอาดหรือเปลี่ยนชุดคีย์แคปตามความชอบ อย่างไรก็ตาม เมื่อประกอบกลับ ผู้ใช้อาจใส่คีย์แคปผิดตำแหน่งได้ง่าย เพราะคีย์แคปตัวอักษรส่วนใหญ่มีขนาดและรูปทรงเหมือนกัน (ขนาด 1u) จึงสลับกันได้โดยไม่มีสิ่งใดขัดขวาง เช่น ตัวอักษร A กับ S สลับช่องกัน

การตรวจสอบด้วยตาทีละปุ่มเป็นวิธีที่ช้า และพลาดได้ง่ายโดยเฉพาะเมื่อมีเพียงหนึ่งคู่ที่สลับกันจากทั้งหมด 26 ตัวอักษร บางครั้งผู้ใช้มาพบความผิดพลาดเมื่อพิมพ์งานแล้วตัวอักษรไม่ตรงกับที่กด ซึ่งเสียเวลาและสร้างความรำคาญ

### 1.1.1 ปัญหาหรือข้อจำกัดที่ต้องการปรับปรุง

1. **การตรวจด้วยตาช้าและพลาดง่าย** โดยเฉพาะเมื่อผิดเพียงหนึ่งคู่จากทั้งหมด 26 ตัวอักษร ผู้ใช้มักพบความผิดพลาดตอนพิมพ์งานแล้วเท่านั้น
2. **ภาพถ่ายมีมุมมองเฉียง** ตำแหน่งและขนาดของปุ่มในภาพไม่สม่ำเสมอ จึงเทียบกับตำแหน่งที่ควรเป็นโดยตรงไม่ได้
3. **ตัวอักษรบนคีย์แคปเป็นข้อความสั้นเพียงตัวเดียว** บนฟอนต์หลากหลาย มีไฟ RGB สะท้อน และบางรุ่นมีอักษรไทยร่วมบนปุ่มเดียวกัน ตัวอ่านข้อความทั่วไป (OCR) ไม่ได้ออกแบบมาสำหรับสภาพนี้
4. **ปุ่มที่ถูกสลับจะมองไม่เห็นว่าสลับ** ถ้าจับคู่ปุ่มกับช่องด้วยตัวอักษรที่อ่านได้ เพราะปุ่มที่ถูกสลับจะถูกจับคู่ตามตัวอักษรของตนเอง
5. **การแจ้งผิดทั้งที่ถูกทำให้ผู้ใช้เสียความเชื่อถือ** ระบบจึงต้องบอกได้ว่า "ไม่แน่ใจ" แทนการเดา
6. **ไม่มีเครื่องมือที่ผู้ใช้ทั่วไปใช้ได้สะดวก** ต้องมีช่องทางถ่ายภาพ แสดงผล และบอกว่าควรแก้ไขอย่างไร

> **หมายเหตุ:** งานนี้ตรวจเฉพาะตำแหน่งคีย์แคปทางกายภาพ ไม่ใช่การตรวจ key mapping ของระบบปฏิบัติการหรือความเสียหายของสวิตช์

### 1.1.2 แนวคิดและแนวทางการแก้ปัญหา (Solution)

คณะผู้จัดทำจึงมีแนวคิดนำเทคโนโลยีปัญญาประดิษฐ์และการประมวลผลภาพมาช่วยตรวจสอบ โดยออกแบบและพัฒนา **KeyCheck** ระบบที่รับภาพถ่ายคีย์บอร์ดหนึ่งภาพ และจุดอ้างอิง 4 จุด (ปุ่ม Q, P, M, Z) ที่ผู้ใช้แตะ แล้วตอบว่าช่องใดมีคีย์แคปถูกต้อง ช่องใดผิด และช่องใดระบบไม่แน่ใจ พร้อมแนะนำว่าควรสลับปุ่มคู่ใด ตัวอย่างเช่น ช่องที่ควรเป็น A พบคีย์แคป S และช่องที่ควรเป็น S พบ A ระบบจะวงทั้งสองตำแหน่งและเสนอให้สลับกลับ

ระบบทำงานเป็นขั้นตอน คือ ปรับภาพให้ตรงด้วย Homography → ตรวจจับกรอบคีย์แคปด้วย YOLO11n → อ่านตัวอักษรด้วยตัวจำแนก ResNet18 → จับคู่ปุ่มกับ 26 ช่องด้วยตำแหน่ง (Hungarian algorithm) → ตัดสินผลรายช่อง โดยมีกลไกงดตอบและปฏิเสธภาพที่ layout ไม่เข้ากัน และมีเว็บแอปพลิเคชันให้ผู้ใช้ถ่ายภาพ แตะจุด และดูผลซ้อนบนภาพ

### 1.1.3 Solution ช่วยแก้ปัญหาที่ระบุไว้ได้อย่างไร

| ปัญหา (ข้อ) | แนวทางในระบบ | ผลที่ได้ / สถานะหลักฐาน |
| --- | --- | --- |
| 1 ตรวจด้วยตาช้าและพลาดง่าย | ถ่ายภาพเดียว ระบบตรวจทั้ง 26 ช่อง วงปุ่มที่ผิด และแนะนำการสลับ (swap pair / cycle) | พัฒนาครบ; ตัวเลขความถูกต้องของ S2/S3 `[รอตัวเลข]` (หัวข้อ 4.4) |
| 2 มุมมองเฉียง | ปรับภาพด้วย Homography จาก 4 จุด ไปยังพิกัดหน่วยปุ่ม (u) | 4 จุดทำนายตำแหน่งปุ่มอื่นได้คลาดส่วนใหญ่ต่ำกว่า 0.25u (หัวข้อ 3.2.3) |
| 3 อ่านตัวอักษรเดี่ยวยาก | ตัวจำแนก ResNet18 27 คลาส (A–Z + OTHER) พร้อมอักษรไทยสังเคราะห์ตอนฝึก | OCR สำเร็จรูปได้สูงสุด 0.82 แต่ปฏิเสธ ≥ 16% จึงเปลี่ยนตัวอ่าน; accuracy ของตัวจำแนก `[รอตัวเลข]` (หัวข้อ 4.1–4.2) |
| 4 ปุ่มสลับมองไม่เห็น | จับคู่ปุ่มกับช่องด้วยตำแหน่งอย่างเดียว (Hungarian) แล้วจึงเทียบตัวอักษร | ออกแบบและมี unit test ของ matching/decision (หัวข้อ 2.5) |
| 5 แจ้งผิดทั้งที่ถูก | สถานะ "ไม่แน่ใจ", ปฏิเสธเมื่อ layout ไม่เข้ากัน, จูน threshold ให้ false-alarm ≤ 2% | ภาพ corsair14: `uncertain` 12 ช่อง แต่ `incorrect` เป็นศูนย์ (หัวข้อ 4.9) |
| 6 ไม่มีเครื่องมือใช้ง่าย | เว็บแอป: ถ่ายภาพ → แตะ 4 จุด → ดูผลซ้อนภาพ พร้อมข้อความภาษาไทย | พัฒนาแล้ว; ยังไม่ได้ทดสอบกับผู้ใช้จริง (หัวข้อ 4.7–4.8) |

ตารางที่ 1 แสดง ปัญหาที่ต้องการปรับปรุงและแนวทางการแก้ปัญหาของ KeyCheck

## 1.2 วัตถุประสงค์

1. เพื่อสร้างชุดข้อมูลและกระบวนการเตรียมข้อมูลภาพคีย์บอร์ดหลายรุ่นพร้อมกรอบ (bounding box) และ ground truth ตำแหน่ง A–Z
2. เพื่อฝึกและเปรียบเทียบตัวตรวจจับ (detector) อย่างน้อย 2 สถาปัตยกรรม
3. เพื่ออ่านตัวอักษรบนปุ่มและตรวจการประกอบผิดตำแหน่ง
4. เพื่อออกแบบระบบที่แสดงสถานะ "ไม่แน่ใจ" เมื่อหลักฐานไม่พอ แทนการเดาว่าปุ่มถูกหรือผิด
5. เพื่อพัฒนาเว็บแอปพลิเคชันต้นแบบสำหรับถ่ายภาพ อัปโหลด และแสดงผลการตรวจ
6. เพื่อประเมินทั้งรายโมดูลและผลลัพธ์ปลายทาง รวมถึงประเมินบนคีย์บอร์ดที่ไม่เคยเห็นในการฝึก

### คำถามวิจัย

1. Detector ใดให้ผลตรวจคีย์แคปผิดดีที่สุดภายใต้ทรัพยากรที่มี
2. การเพิ่ม Detector ช่วยเหนือ Baseline ที่ตัดภาพตาม Layout โดยไม่ใช้ Detector หรือไม่
3. Error ส่วนใหญ่เกิดจากขั้นใด: การปรับภาพ การตรวจกรอบ การอ่านตัวอักษร หรือการจับคู่ตำแหน่ง
4. แสง มุมภาพ และรูปแบบการสลับที่ไม่อยู่ในชุดฝึกส่งผลอย่างไร
5. ระบบทำงานบนคีย์บอร์ดที่ไม่เคยเห็นได้ดีเพียงใด

## 1.3 ขอบเขตของโครงงาน

1. รองรับคีย์บอร์ด QWERTY แบบแถวเยื้อง (ANSI/ISO) โดยตรวจ **เฉพาะตัวอักษรอังกฤษ A–Z รวม 26 ตำแหน่ง** ปุ่มที่มีอักษรไทยร่วมถูกอ่านเฉพาะตัวละติน
2. ใช้ Layout อ้างอิงแบบ generic letter-block ในหน่วยปุ่ม (1u) ร่วมกันทุกรุ่น
3. ผู้ใช้เป็นผู้แตะจุดอ้างอิง 4 จุด (ปุ่ม Q, P, M, Z) บนภาพเอง ยังไม่มีการตรวจหามุมอัตโนมัติ
4. ใช้งานแบบกดถ่ายแล้วรอผล ไม่ใช่การตรวจแบบ real-time และประมวลผลที่ฝั่ง Backend
5. **ฝึกและประเมินด้วยข้อมูลตัวแทน (proxy)** คือภาพคีย์บอร์ด QWERTZ จาก Kaggle เนื่องจากยังไม่ได้เก็บภาพ QWERTY ที่ถ่ายเอง ผลการทดลองจึงแสดงว่า pipeline ทำงานและเลือกโมเดลได้ ไม่ใช่ความแม่นยำของระบบกับภาพถ่ายจริง
6. รายงานผลบนชุด Validation เท่านั้น ชุด Test ถูกล็อกไว้และยังไม่ได้รัน
7. ไม่รองรับ Layout อื่นนอกจาก QWERTY แถวเยื้อง (เช่น Dvorak, Colemak, Ortholinear, Split) ระบบพยายามตอบ `LAYOUT_MISMATCH` เมื่อตรวจพบว่าไม่เข้ากัน แต่ **ยังมีช่องว่างที่ทราบแล้ว** คือคีย์บอร์ดแบบ Ortholinear ที่ผู้ใช้แตะจุดถูกต้องจะยังไม่ถูกปฏิเสธ (ดูหัวข้อ 5.3)
8. การฝึกโมเดลทำบนเครื่องคอมพิวเตอร์ส่วนบุคคลที่มี GPU ไม่ได้ใช้ Google Colab
